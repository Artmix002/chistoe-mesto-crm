Рабочий документ для новых задач, идей и решений по развитию приложения.

## Глубокий аудит текущего состояния

Дата аудита: 2026-09-02.

### Что уже работает

- Основные разделы CRM открываются: Dashboard, клиенты, сделки, записи,
  бухгалтерия, склад, сообщения и тест-бот.
- Google Calendar умеет создавать, изменять и отменять записи, проверять
  пересечения по мастеру и автомобилю и хранить ID клиента/сделки.
- Справочник услуг содержит длительность, четыре класса цен, материалы и
  отдельные правила для бота.
- Локальные данные сохраняются в JSON, есть offline-очередь, повторы запросов,
  резервное восстановление, роли и аудит действий.
- AI-провайдер совместим с OpenAI API, использует GPT-5.4 и не отвечает при
  отсутствии подтверждённого факта.
- `flutter analyze` проходит без ошибок; текущий набор тестов покрывает 110
  сценариев.

### Критические разрывы для production

1. **VK не работает как real-time интеграция.** Диалоги загружаются при запуске
   или вручную; Long Poll/webhook для входящих событий не запущен. Новое
   сообщение клиента не создаёт задачу, клиента или запись автоматически.
2. **Напоминания зависят от открытой CRM.** Проверка выполняется локальным
   таймером раз в минуту. После закрытия приложения напоминание не гарантируется.
3. **Нет единого backend для нескольких операторов.** Apps Script хранит
   снимки; при одновременной работе более свежие данные могут быть заменены
   старым снимком. Нужны версии и разрешение конфликтов.
4. **Google Calendar загружается ограниченно.** Используется один запрос до
   100 событий без полноценной пагинации и фоновой синхронизации изменений.
5. **Ошибка доставки уведомления о новой записи не всегда ставится в очередь.**
   Запись сохраняется, но сбой отправки в чат сотрудников может остаться только
   в интерфейсе.
6. **Правила услуг требуют обновления backend-схемы.** Поле `botInstructions`
   есть в приложении, но его нужно добавить в `SheetsSchema`, Apps Script и
   миграцию листа `CRM_ServiceCatalog`.
7. **Сделки частично хранятся как строки.** Это ограничивает связь клиента,
   услуги, исполнителей, оплат и истории перерасчётов.
8. **Shared Preferences не является транзакционной БД.** Для больших объёмов,
   поиска, блокировок и восстановления отдельных записей нужна локальная БД.
9. **При отсутствии защищённого endpoint остаётся публичный gviz CSV.** Для
   production этот fallback следует отключить после миграции.
10. **Основная логика всё ещё сосредоточена в `lib/main.dart` (~12 тысяч строк).**
    Это повышает риск регрессий и усложняет дальнейшую разработку.

## Целевая архитектура полноценной CRM

### Данные

- PostgreSQL или совместимая серверная БД как источник истины.
- REST/JSON API с авторизацией, ролями, аудитом и версией схемы.
- Google Sheets — экспорт, резервная копия и сверка, а не рабочая БД.
- Google Calendar — внешний календарь с двусторонней синхронизацией по ID.
- Локальная БД/кэш для offline-режима; Shared Preferences оставить для настроек.

### Доменные сущности

`Client`, `Vehicle`, `Service`, `Deal`, `Appointment`, `Payment`, `Expense`,
`StockItem`, `MessageThread`, `Message`, `Employee`, `KnowledgeRule`.

У каждой сущности обязательны `id`, `createdAt`, `updatedAt`, `version`, `source`
и `updatedBy`. Удаление — архивирование с журналом, а не физическое удаление.

### Интеграции

- VK Callback API или Long Poll на сервере с очередью входящих событий.
- Единый inbox с дедупликацией по `channel + externalMessageId`.
- Исходящие сообщения через очередь с idempotency key, статусами и retry.
- Серверный планировщик напоминаний, чтобы они работали при закрытой CRM.
- AI получает только разрешённый контекст и всегда поддерживает перевод сотруднику.

## Предлагаемый порядок доработки

### Этап 1 — надёжность данных

- Добавить `botInstructions` в `SheetsSchema`, Apps Script и все экспорты.
- Ввести миграции схемы и проверку версии перед синхронизацией.
- Завершить доставку VK-уведомлений через локальную очередь.
- Делать резервную копию перед каждой заменой облачного снимка.
- Разделить `main.dart` на состояние, репозитории, сервисы и экраны.

### Этап 2 — серверный контур

- Развернуть backend с PostgreSQL и авторизацией.
- Перенести туда клиентов, сделки, записи, финансы, склад и сообщения.
- Добавить optimistic locking, журнал событий и восстановление после сбоя.
- Оставить Google Sheets экспортом и резервным каналом.

### Этап 3 — VK и коммуникации

- Подключить Callback API/Long Poll и обработчик событий.
- Автоматически создавать/обновлять клиента по VK peer ID и телефону.
- Добавить статусы диалога: новый, ожидает ответа, назначен, записан,
  закрыт, передан сотруднику.
- Включать AI-ответ только для явно разрешённых каналов.

### Этап 4 — полный цикл записи

- Команда или кнопка в VK: «записать», выбор услуги, класса автомобиля,
  времени и мастера.
- Онлайн-проверка свободных слотов и подтверждение клиентом.
- Создание записи в backend и Google Calendar одной идемпотентной операцией.
- Уведомление сотрудников, клиента и серверного планировщика напоминаний.

### Этап 5 — сделки, финансы и отчётность

- Перевести сделки на типизированную модель с несколькими услугами и выплатами.
- Связать сделку с записью, клиентом, оплатой и расходом материалов.
- Добавить закрытие периода на сервере и неизменяемый финансовый журнал.
- Формировать отчёты по выручке, марже, мастерам, услугам и загрузке.

## Критерии production-ready

- Два сотрудника могут одновременно работать без потери и перезаписи данных.
- Входящее сообщение VK появляется в CRM не позднее 10 секунд.
- Новая запись создаётся один раз даже при повторной доставке события.
- Напоминания отправляются при закрытом приложении и имеют журнал доставки.
- Любое изменение связано с пользователем, временем и источником.
- Сценарий «сообщение → клиент → запись → сделка → оплата → отчёт» проходит
  без ручного редактирования Google Sheets.
- При потере сети данные не теряются и доставляются после восстановления.
- Публичный gviz-доступ отключён, секреты отсутствуют в репозитории и логах.
